# PLAN.md — План выполнения тестового задания «Продуктовая ферма»

> Источник требований: `TZ.md` (сжатая версия) и полное ТЗ в
> `Продуктовая ферма — тестовое задание · Атвинта.md`. Правила работы: `AGENTS.md`.
> Каждый этап = код → автотест → коммит (`feat(scope): §N ...`) → запись в `DEVLOG.md`
> → ручная проверка человеком перед переходом к следующему этапу.

## Зафиксированные решения

| Параметр | Решение |
|---|---|
| Идея §1 (сквозной сценарий) | Разбор обращений: обращение → ИИ-классификация → микросервис-валидатор правил → сохранение → показ пользователю |
| Основная метрика | Время на операцию (обработку обращения) |
| Метрика качества | Доля корректных классификаций |
| LLM пайплайна | `z-ai/glm-5.3-flash` через routerai.ru (эндпоинт Novita) |
| STT (голос → текст) | `microsoft/mai-transcribe-2` через routerai.ru (~0.0031 ₽/сек аудио, русский поддерживается) |
| БД | Postgres 16 в Docker на VPS |
| Хостинг | VPS: Nuxt SSR + persistent worker, docker-compose |
| HTTPS | Caddy, домен `idea-factory.nikgretenok.online` (DNS настраивает владелец) |
| Секреты | В `.env` на сервере; в репозитории только `.env.example` без значений |

## Стек

- **Nuxt 3/4 + Nitro** — UI и server routes (API).
- **LangGraph.js** — граф ролей агентов (§7 TZ). Состояние графа чекпоинтится в Postgres
  → требование «перезапуск обработчика продолжает с последнего корректного шага» (§8 TZ)
  выполняется штатным механизмом resume.
- **shadcn-vue + Tailwind v4** — UI по токенам `DESIGN.md`.
- **Расчётный модуль** — детерминированный TS на сервере (без LLM): математическая модель
  (формулы видны в отчёте), bootstrap/CI с фиксированным seed, 3 сценария.
- **Микросервис-валидатор** — отдельный Node-процесс с HTTP-контрактом (вход/выход/версия),
  отдельный контейнер в docker-compose → заодно демонстрация изоляции выполнения (§11 TZ).
- **Очередь** — таблица `queue_jobs` в Postgres + persistent worker-процесс: опрос,
  приоритеты high/medium/low, anti-starvation, идемпотентные запуски.

## Зависимости этапов

- Этапы 0–1 не блокируются ничем (уже начаты).
- Этап 3 зависит от STT-ключа (есть) и этапа 2 (схема БД).
- Этапы 5–7 зависят от 4 (очередь/оркестратор).
- Этап 8 может идти параллельно с 5–7 (моки данных).
- Этап 9 — после 6–8. Этапы 10–12 — после 9. Этап 13 — финал.

## Допущения (реестр, пополняется в TZ.md §15)

1. Брендбук не передан → визуальная основа: референс Arounda через `DESIGN.md`.
2. Хостинг VPS вместо serverless — из-за требования persistent worker (§8 TZ).
3. Стресс-тест на 10 одновременных идеях не проводим — проверяем корректность логики
   очереди на меньшем числе (разрешено §15 TZ).
4. Второй вариант ИИ-решения для сравнения прогонов — та же модель с другим промптом/
   составом цепочки (допустимо по §2.5 ТЗ: «варианты могут различаться моделью, промптом
   или составом цепочки»).
